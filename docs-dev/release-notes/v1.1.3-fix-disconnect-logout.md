# v1.1.3 — Fix Disconnect Logout Callback Loop

**Date:** 2026-05-08
**Status:** Completed
**Branch:** `develop`
**Tracking doc:** `docs-dev/tasks/task-113-fix-disconnect-logout.md`

## Background

Disconnecting from the avatar menu behaved differently between localhost and the Vercel preview deployment.

- On `localhost:3000`, clicking **Disconnect** quickly returned the user to the public landing page.
- On `https://dash-dev.infrafund.net/`, clicking **Disconnect** could leave the browser on a blank screen with a callback-style URL containing `openfortAuthProviderUI`, `access_token`, and `user_id`.
- Reloading that blank page could log the user back in and restart the 5-step auth bootstrap flow.

The root cause was that the app treated a stale Openfort OAuth callback URL left behind after sign-out the same way it treated a legitimate post-login callback.

## Root cause

Openfort’s SDK uses callback query parameters such as:

- `openfortAuthProviderUI`
- `access_token`
- `user_id`
- `error`

The app already had logic in `MainLayout` and `AuthSessionProvider` that checked for `openfortAuthProviderUI` in the URL to mask the page and start the auth bootstrap flow. That worked for real OAuth login returns, but it did not distinguish them from a stale callback-shaped URL encountered immediately after logout.

As a result:

1. The backend refresh cookie was revoked.
2. The browser could still land on a callback-style Openfort URL.
3. On reload, the SDK could consume those params again and restore credentials.
4. The user appeared to be logged back in even though they had just disconnected.

## Changes

### 1. Added Openfort callback state helper

New file:

- `src/lib/openfort-oauth-state.ts`

This helper centralizes client-side detection and sanitization of Openfort callback URLs. It now:

- classifies the current URL as:
  - `oauth_login_callback`
  - `stale_oauth_params`
  - `none`
- tracks a short-lived logout marker in `sessionStorage`
- strips stale Openfort callback params from the URL via `history.replaceState`

### 2. Marked explicit logout before calling Openfort sign-out

Updated:

- `src/components/auth/auth-session-provider.tsx`

Before calling `signOut()`, the app now stores a short-lived `infrafund:openfort-logout-in-progress` marker. This allows the next page load to tell the difference between:

- a genuine OAuth login callback
- a stale callback URL reached as part of disconnect flow

### 3. Sanitized stale callback URLs on mount

Updated:

- `src/components/auth/auth-session-provider.tsx`

On mount, the provider now checks the callback classification early. If the URL is callback-shaped but the logout marker is present, it will:

- remove `openfortAuthProviderUI`, `access_token`, `user_id`, and `error` from the URL
- clear the logout marker
- clear local auth session state
- close the Openfort modal
- remain in the unauthenticated state instead of restarting auth bootstrap

This prevents the reload-to-log-back-in behavior seen on Vercel preview.

### 4. Narrowed callback masking logic in layout

Updated:

- `src/components/main-layout.tsx`

The layout no longer treats any URL containing `openfortAuthProviderUI` as an active login callback. It now only masks the page when the helper identifies a legitimate `oauth_login_callback`.

This avoids the blank-screen state during logout returns while preserving the intended loading behavior for real Google login callbacks.

## Expected behavior after this release

After clicking **Disconnect**:

- the app should return to a clean logged-out route
- stale Openfort callback params should not remain in the address bar
- refreshing the page should not silently restore the Openfort session
- valid login callbacks should still trigger the normal 5-step sign-in/bootstrap flow
