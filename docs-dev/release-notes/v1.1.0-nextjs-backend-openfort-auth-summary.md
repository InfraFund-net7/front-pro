# v1.1.0 Next.js Backend and Openfort Auth

This release consolidates the backend migration and the Openfort-based authentication work that now defines the promoted `develop` branch. It captures the path from the late Next.js backend migration phases through the Openfort auth, wallet, UX, and deployment hardening that replaced the retired Go backend.

## Summary

InfraFund now runs as a single Next.js 16 application with App Router pages, same-origin `/api/v1` routes, PostgreSQL access through Prisma, and Openfort as the identity and embedded-wallet provider. The app owns its own JWT access tokens, refresh-cookie sessions, account/profile CRUD, lockout handling, cleanup cron route, and public form APIs, while Openfort owns user authentication and wallet primitives.

The Openfort integration remains intentionally qualification-gated: `connectOnLogin: false` prevents wallet creation during initial sign-in, and wallet creation or reconnection happens only after the app determines whether the user is an existing qualified user or completes the onboarding flow for a new qualified user.

## What shipped

### Backend migration completion

- Completed the final migration phases that retired active runtime dependence on the old Go backend.
- Standardized frontend backend calls on same-origin `/api/v1/...` routes.
- Removed remaining active runtime and deployment wiring for legacy backend URLs such as `NEXT_PUBLIC_API_BASE_URL`, `API_URL`, direct old `/v1` usage, and `backpro` references.
- Kept the backend inside the existing Next.js app instead of introducing a separate service.
- Preserved the layered server structure for env validation, HTTP helpers, auth/session management, repositories, services, Prisma DB access, and Openfort session verification.

### Next.js-owned auth and session model

- Confirmed the two-layer auth model:
  - Openfort verifies user identity and provides access tokens plus embedded-wallet capabilities.
  - InfraFund exchanges verified Openfort identity for app-owned JWT access tokens and httpOnly refresh-cookie sessions.
- Implemented and hardened the core auth endpoints and flows around:
  - Openfort session check
  - Openfort session exchange
  - refresh / logout
  - protected profile/account endpoints
  - account deletion with session revocation and best-effort Openfort cleanup
- Added lightweight account lockout enforcement on the Openfort exchange path.
- Added protected cron cleanup support for expired lockouts, stale audit logs, and expired or long-revoked sessions.

### Lean Openfort integration

- Kept the provider stack aligned around `QueryClientProvider` -> `WagmiProvider` -> `OpenfortWagmiBridge` -> `OpenfortProvider`.
- Preserved `connectOnLogin: false` so login does not automatically provision wallets before qualification succeeds.
- Kept automatic recovery and token-verified Shield encryption-session issuance through a same-origin Next.js route.
- Removed obsolete server env aliases from the Go-era Openfort setup and aligned deployment chain selection by environment.

### Openfort registration/login functional fixes

- Fixed the embedded-wallet iframe 403 issue caused by missing `Referer` data during iframe creation.
- Applied a narrowly targeted client-side workaround for the Openfort iframe until the upstream SDK issue is resolved.
- Fixed returning-user wallet reconnection so existing users no longer land in an authenticated app session with `[Not connected]` wallet state.
- Ensured wallet creation/reconnection always goes through the explicit embedded-wallet `create()` path required by the qualification-gated design.

### Openfort auth UX cleanup

- Replaced noisy multi-stage loading and overlapping auth UI with a single progress-modal flow.
- Added ordered auth progress steps across signing in, checking the account, restoring the session, loading the profile, and connecting or setting up the wallet.
- Closed the Openfort modal earlier in the bootstrap flow so users no longer see the confusing intermediate “Connected / Manage wallets” state.
- Smoothed the OAuth callback path so users do not see the landing page flash or a second Google/Openfort modal before the app-owned progress flow takes over.
- Preserved different wallet-step semantics for returning-user reconnect versus first-time wallet setup.

### Account and wallet UX improvements

- Added an avatar menu with Account and Disconnect actions.
- Exposed wallet connection state more clearly in the header.
- Added copyable wallet details and block-explorer links in the account area.
- Reduced dependence on the Openfort-hosted connected-state UI for basic app actions like logout.

### Public-form and landing polish

- Improved landing-page auth copy and login/register messaging.
- Reordered and polished the non-resident form UX.
- Fixed the country dropdown so it renders outside modal bounds and loads the full country list instead of the old truncated default.
- Improved captcha diagnostics, especially for local-domain and configuration troubleshooting.
- Added clearer required-field cues in the non-resident flow.

### Preview deployment database readiness

- Updated prebuild setup so preview deployments can initialize Neon automatically instead of failing against an empty database.
- Added Neon/Postgres compatibility handling for `uuidv7()` where the target database does not expose it as a built-in.
- Ensured schema push and country seeding happen during Vercel builds.
- Prevented log-only `entire/checkpoints/v1` pushes from triggering unnecessary Vercel deployments.

## Key outcomes

- The old Go backend is no longer part of the active frontend/runtime path.
- InfraFund now ships as one Next.js application that owns its backend APIs and sessions.
- Openfort auth now supports the intended qualification-gated flow for both new and returning users.
- Embedded-wallet creation and reconnection work without exposing confusing extra modal states to users.
- Preview deployments can bootstrap their database state automatically instead of failing during login.
- The former `openfort` branch has been promoted to `develop`, making this implementation line the main development baseline.

## Notes

- The Openfort iframe referrer issue still has an upstream dependency; the local workaround remains in place until the SDK ships a native fix.
- Browser-based smoke testing with real Openfort and Shield credentials remains the final verification path for hosted auth, qualification, wallet creation, and recovery behavior.
- Historical release notes for earlier migration phases remain the source of detailed step-by-step implementation history; this file is the consolidated summary for the final Next.js backend plus Openfort-auth baseline.
