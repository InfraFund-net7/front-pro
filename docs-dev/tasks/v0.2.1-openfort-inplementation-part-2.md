# v0.2.1 Openfort Implementation Part 2

**Date:** 2026-03-27
**Status:** Proposed plan
**Predecessor:** `docs-dev/audit-review/v0.2.0-openfort-integration-review-1.md`

## Goal

Finish the Openfort migration so the app uses a single coherent authentication and wallet model across login, app shell, and backend API access.

## Current State

- Openfort provider wiring is structurally correct.
- `/login` uses `OpenfortButton`.
- Automatic recovery endpoint is present.
- Legacy guest header, wallet modal, and bearer-token utilities still exist and remain active in the main app.

## Target Outcome

1. Users authenticate through Openfort and remain authenticated across the app.
2. Protected app routes respect auth state.
3. The header and wallet entry points use Openfort state/components instead of legacy mock flows.
4. Backend API access is either fully aligned with Openfort or the obsolete token path is removed.
5. The app exposes a clear sign-in / sign-out / connected-wallet experience.

## Implementation Plan

### Phase 1 — Decide the auth contract

Define the source of truth for authenticated API requests:

- **Option A — Openfort-only frontend auth:** if backend APIs do not need the legacy `access_token`, remove or bypass the old token utilities and auth proxy routes.
- **Option B — Openfort + backend session exchange:** if backend APIs still require bearer auth, add a frontend/backend handshake that exchanges Openfort-authenticated user state for the backend token expected by existing API routes.

This is the main design dependency for the rest of the work.

### Phase 2 — App-wide auth integration

- Add a shared auth hook/provider wrapper for reading Openfort auth state.
- Redirect authenticated users away from `/login`.
- Guard app routes so unauthenticated users are redirected to `/login`.
- Add loading/fallback handling while Openfort resolves session state.

### Phase 3 — Replace the live legacy wallet UX

- Remove or retire `src/components/connectwallet/connect-wallet-modal.tsx` from the header flow.
- Replace the header wallet action with Openfort-native behavior:
  - `OpenfortButton`, or
  - a small custom account control powered by Openfort hooks.
- Ensure the live wallet entry point is consistent with the login experience.

### Phase 4 — User identity and sign-out

- Replace hardcoded guest text in `src/components/header.tsx`.
- Show user identity from Openfort state.
- Add sign-out behavior using Openfort hooks.
- Confirm the post-sign-out redirect and app state reset.

### Phase 5 — Reconcile or remove legacy auth code

Review and either integrate or remove these legacy paths:

- `src/utils/get-access-token.util.ts`
- `src/utils/interceptors.utils.ts`
- `src/services/api.service.ts`
- `src/app/api/auth/challenge/route.ts`
- `src/app/api/auth/register/route.ts`

If backend session exchange is required, rework them around the new contract. If not, delete dead paths.

### Phase 6 — Config hardening

- Confirm whether external wallets should remain enabled.
- If yes, require/configure `NEXT_PUBLIC_WALLET_CONNECT_PROJECT_ID`.
- Confirm target chains and sponsorship behavior for Base / Base Sepolia.
- Verify environment-variable naming and required runtime fallbacks.

### Phase 7 — Validation

- Run lint, typecheck, prettier, and targeted runtime verification.
- Manually verify:
  - login
  - redirect behavior
  - wallet creation/recovery
  - sign-out
  - header/account state
  - any backend-authenticated API flow kept in scope

## Decisions Needed Before Implementation

1. **Backend auth model:** does the backend still require its legacy bearer token, or can frontend auth be Openfort-only for now?
2. **Wallet UX:** should the header use stock Openfort UI (`OpenfortButton`) or should we preserve a custom InfraFund-styled account control?
3. **External wallets:** keep `AuthProvider.WALLET` enabled now, or ship embedded wallet + Google/email first?
4. **Protected surface:** should all non-`/login` routes require auth immediately, or only a subset for this release?

## Can implementation start now?

**Yes, mostly.**  
I have enough context to implement the frontend-side integration work immediately.

The only meaningful blocker is **Decision #1: the backend auth contract**. If that is still unresolved, I can still complete the UI/app-shell integration first, but I would treat backend API token reconciliation as a separate step gated on that answer.
