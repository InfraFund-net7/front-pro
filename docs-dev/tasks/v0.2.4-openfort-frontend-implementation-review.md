## Architecture Assessment

### Auth Flow

The session orchestration in `auth-session-provider.tsx` is the structural centerpiece. The flow is:

1. Openfort SDK resolves auth state (`useUser`)
2. If authenticated, attempt backend refresh first (session restore)
3. If no backend session, get an Openfort access token
4. Check backend for existing user (`GET /auth/openfort/check`)
5. Existing user → exchange → finalize
6. New user → show questionnaire → on submit, exchange with role/type → wallet creation → finalize

This is clean and matches the plan's mermaid diagram exactly. The deduplicate guard (`bootstrapAttemptKeyRef`) added in `8929654` prevents the duplicate network calls identified during local QA.

### Provider Hierarchy

```
QueryClientProvider
  └─ WagmiProvider
       └─ OpenfortWagmiBridge
            └─ OpenfortProvider (connectOnLogin: false)
                 └─ AuthSessionProvider
                      └─ MainLayout
                           └─ children
```

The `AuthSessionProvider` wraps `MainLayout` and renders the `QualificationQuestionnaire` as a sibling to `children`, which is correct — the modal overlays the page content without being affected by the public/private route guard.

### Route Guard

`main-layout.tsx` implements a client-side route guard:
- Public routes: `/`, `/login`
- Authenticated users on public routes → redirect to `/home`
- Unauthenticated users on private routes → redirect to `/`
- During onboarding (`needs_onboarding`) → hide the public landing content, show only the questionnaire modal
- During wallet creation → show "Setting up your wallet..." loading state

This is straightforward and appropriate for an SDK-based auth model where session state is not available server-side.

### Backend Client

`backend-auth-client.ts` is a clean, fetch-based client with:
- `credentials: 'include'` on all requests (cookie-based refresh)
- Bearer token passed via `Authorization` header
- Consistent error extraction from response bodies
- Dual base URL support (`NEXT_PUBLIC_API_BASE_URL` / `NEXT_PUBLIC_BASE_URL`)

## Open Items

### Carried from prior review — still open

#### N1. Role normalization: `client` → `project_owner` (medium priority)

**File:** `src/components/auth/auth-session-provider.tsx:67-69`

The questionnaire uses `client` as the role value for "Raise Funds (Project Developer)". `normalizeRole` maps it to `project_owner` before sending to the backend. The task plan only specifies mapping `dao` → `governance`; it lists `client` as the backend value for that option.

**Risk:** If the backend expects `client`, new users selecting "Raise Funds" will be provisioned with the wrong role (`project_owner`).

**Action needed:** Verify with the backend which role value it expects. If `client`, remove the `client` → `project_owner` mapping. If `project_owner`, update the task plan to document the deviation.

#### N2. `wallets.length` in dependency array (low priority)

**File:** `src/components/auth/auth-session-provider.tsx:149`

`createWalletIfNeeded` depends on `wallets.length` from the `useEthereumEmbeddedWallet` hook. Since `.length` is a primitive derived from the hook, the memoized callback could evaluate a stale value if invoked twice before a re-render. Practical risk is low — the retry path repopulates `pendingWalletCreation` which bypasses this code path.

**Action:** Monitor. No code change needed unless duplicate wallet-creation calls appear in logs.

#### N3. Organization company name validation on wrong step (low priority)

**File:** `src/components/auth/qualification-questionnaire.tsx:225-228`

If a user clears the company name after advancing to step 3 (via browser devtools or race condition), the error appears on step 3 instead of step 2. The step 2 Continue button is already disabled when the company name is empty, so reaching this state requires deliberate manipulation.

**Action:** Accept current behavior or add a guard that resets to step 2 if company name is empty on step 3 submit.

#### N4. `BackendCountryRecord` dual-casing (low priority)

**File:** `src/lib/backend-auth-client.ts:17-30`

The interface handles both PascalCase and snake_case keys. This is defensive code that exists because the backend response format wasn't confirmed at implementation time. Once the backend response casing is stable, simplify to match.

**Action:** After local QA confirms the actual response shape, simplify the interface and remove `normalizeCountry`.

### New findings

#### N5. Server-side Shield env vars not in Dockerfile (deployment gap)

**Files:** `deployment/Dockerfile`, `src/app/api/auth/encryption-session/route.ts`

The Dockerfile passes `NEXT_PUBLIC_*` vars as build args (correct for client-side inlining). However, the server-side Shield vars (`SHIELD_SECRET_KEY`, `SHIELD_ENCRYPTION_SHARE`, `SHIELD_URL`) are needed at **runtime** by the encryption-session API route. These are not build args — they must be injected as runtime environment variables in the Docker Compose / deployment configuration.

The Dockerfile itself is correct (these shouldn't be build args). But neither deploy workflow nor the Dockerfile documents this. The `.env.example` lists them, and the test plan documents them, but the deployment path should have a checklist or comment confirming they'll be injected at runtime.

**Risk:** Wallet creation will fail in deployed environments if the runtime env vars are not set in the Docker Compose or orchestration layer.

**Action:** Verify that the Docker Compose files referenced in the workflows (`${{ vars.DOCKER_COMPOSE_PATH_DEVELOP }}`, `${{ vars.DOCKER_COMPOSE_PATH_PRODUCTION }}`) pass `SHIELD_SECRET_KEY` and `SHIELD_ENCRYPTION_SHARE` as environment variables to the container.

#### N6. Dual base URL env var naming

**File:** `src/lib/backend-auth-client.ts:92-96`

`getApiBaseUrl()` falls back from `NEXT_PUBLIC_API_BASE_URL` to `NEXT_PUBLIC_BASE_URL`. The Dockerfile and workflows use `NEXT_PUBLIC_API_BASE_URL`. The `.env.example` uses `NEXT_PUBLIC_BASE_URL`. The test plan uses `NEXT_PUBLIC_BASE_URL`.

There are two names for the same thing. This will work (the fallback catches both), but it creates confusion.

**Action:** Standardize on one name. `NEXT_PUBLIC_API_BASE_URL` aligns with the Dockerfile/workflows; `NEXT_PUBLIC_BASE_URL` aligns with `.env.example` and docs. Pick one, update the other references, and remove the fallback.

**Resolved (v0.2.5):** Standardized on `NEXT_PUBLIC_API_BASE_URL`. Removed `NEXT_PUBLIC_BASE_URL` fallback from `getApiBaseUrl()`, updated `.env.example`, and updated all doc references.

#### N7. `package.json` version not bumped

**File:** `package.json:3`

The package version is still `0.1.0`. The task documents reference this work as v0.2.2/v0.2.3, and the branch carries a substantial feature addition. This is cosmetic but could cause confusion in build artifacts or deployment logs.

**Action:** Consider bumping to `0.2.3` or similar to align with the task versioning.
