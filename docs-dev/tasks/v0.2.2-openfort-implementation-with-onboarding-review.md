### Needs Attention

#### N1. Role normalization: `client` → `project_owner`

**File:** `src/components/auth/auth-session-provider.tsx:67-68`

`normalizeRole` maps `client` → `project_owner`. The task plan lists the backend role values as `client`, `investor`, `contractor`, `governance`. It only mentions mapping `dao` → `governance`. If the backend expects `client` (not `project_owner`), new users selecting "Raise Funds" will be created with the wrong role.

**Action:** Verify with the backend what role value it expects for the "Raise Funds / Project Developer" option. If `client`, change the mapping. If `project_owner`, document the deviation from the plan.

#### N2. `wallets.length` in useCallback dependency

**File:** `src/components/auth/auth-session-provider.tsx:145`

`createWalletIfNeeded` depends on `wallets.length`. Since `wallets` comes from a hook, its `.length` is a primitive that won't update inside the memoized callback until the next render. The `wallets.length > 0` short-circuit at line 128 could evaluate against a stale value if the function is called twice (e.g. via retry after wallet creation actually succeeded).

**Risk:** Low — the current flow calls `finalizeAuthenticatedSession` right after `create()`, so this path is unlikely to be hit. Worth monitoring if duplicate wallet-creation calls appear in logs.

#### N3. Organization company name validation appears on the wrong step

**File:** `src/components/auth/qualification-questionnaire.tsx:225-228`

If a user selects "Organization" in step 2, leaves the company name empty, advances to step 3, and submits — the error "Company name is required" appears on the confirmations step (step 3), not on step 2 where the field lives. The step 2 Continue button is already disabled when `isOrganizationReady` is false, so this case requires the user to go back, fill in a name, clear it, and advance — unlikely but possible.

**Action:** Decide whether to add a guard that resets to step 2 if company name is empty when step 3 submit fires, or accept the current behavior.

#### N4. `BackendCountryRecord` dual-casing

**File:** `src/lib/backend-auth-client.ts:17-30`

The interface handles both PascalCase (`ID`, `Name`, `Iso`) and snake_case (`id`, `name`, `iso`) keys, and `normalizeCountry` resolves both. This is defensive but adds complexity. Once the backend response format is confirmed stable, simplify to whichever casing it actually returns.

#### N5. `bootstrapSession` dependency array and potential double-fire

**File:** `src/components/auth/auth-session-provider.tsx:148, 254`

`bootstrapSession` depends on `getAccessToken` from the Openfort hook. If that function's identity changes between renders, the callback recreates and the `useEffect` re-fires. The `isLoading`/`isAuthenticated` guards prevent visible double-fire, but duplicate check/exchange network calls could appear in logs.

**Action:** Monitor during QA. If duplicates appear, wrap `bootstrapSession` invocation in an `isMounted` ref guard or deduplicate with a status check.
