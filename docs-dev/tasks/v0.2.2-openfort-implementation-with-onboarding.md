# v0.2.2 Openfort Implementation With Onboarding

**Date:** 2026-04-12  
**Status:** Approved plan  
**Supersedes:** `docs-dev/tasks/v0.2.1-openfort-implementation-part-2.md`

## Goal

Finish the Openfort rollout with a lean onboarding flow that:

1. keeps Openfort as the default auth UX
2. uses one auth entry point on the public homepage
3. checks whether the Openfort user already exists before showing onboarding
4. sends only new users through qualification
5. defers wallet creation until after qualification
6. adds a post-auth profile verification/completion step

## Product Direction

- `/` becomes the public landing page.
- `/login` stays available but only redirects to `/`.
- Homepage auth uses a single Openfort entry point instead of separate login/register buttons.
- Existing users should go straight from Openfort auth into the app.
- New users should be qualified before InfraFund fully provisions them.
- Unqualified users should be sent to the existing waitlist flow.
- Qualified users should complete a lightweight account verification page after auth.
- Phone number is not required in this phase.

## Clean / Lean / Defaults-First Principles

- Keep Openfort stock UI and modal behavior wherever possible.
- Do not restore the old Particle cookie handoff or popup chain.
- Keep frontend state local (`sessionStorage` for short-lived onboarding intent only).
- Keep backend responsibility limited to app identity, session, profile, and authorization.
- Do not couple onboarding to custom wallet UI.

## Backend Role

The backend is not the wallet creator. Its job is to:

1. verify the Openfort session/token
2. find the InfraFund user by `openfort_user_id`
3. create or refresh the InfraFund app session
4. expose app-level identity/status/profile endpoints
5. store app-specific profile data such as role, type, and completion fields

Openfort remains responsible for authentication, embedded wallet lifecycle, and recovery.

## Target User Flow

```mermaid
flowchart TD
  LP[Public landing /] --> OB[Single Openfort button]
  OB --> OA[Openfort auth]
  OA --> CK[Backend check by openfort_user_id]
  CK -->|existing user| EX[Backend session exchange]
  EX --> APP[/home]
  CK -->|new user| QZ[Qualification questionnaire]
  QZ -->|qualified| NX[Backend session exchange with role/type]
  NX --> PF[Profile verification page]
  PF --> WC[Create or connect embedded wallet]
  WC --> APP
  QZ -->|not qualified| WL[Waitlist submit with captcha]
```

## Frontend Plan

### 1. Public/auth routing cleanup

- Make `/` public.
- Redirect `/login` to `/`.
- Replace the current implicit private-route rule with an explicit private-route list.

### 2. Single Openfort entry point

- Keep one Openfort-driven button on the landing page.
- Let Openfort handle provider selection and auth UI.
- Do not reintroduce custom login/register auth screens.

### 3. Existing-user detection before onboarding

- After Openfort auth succeeds, call the backend to determine whether the user already exists.
- If the user exists, complete backend session exchange and enter the app.
- If the user is new, hold the auth session client-side and continue to onboarding before final app provisioning.

### 4. Qualification flow for new users only

- Rebuild the old qualification logic as a lean in-app modal/state flow.
- Derive `role` and `type` from questionnaire answers.
- Store the short-lived onboarding payload in `sessionStorage` until exchange completes.
- If the user is not qualified, submit to the existing waitlist endpoint and stop there.

### 5. Profile verification/completion page

- After first successful qualified exchange, route the user to an account verification page.
- Prefill with Openfort-provided name/email when available.
- Let the user confirm or complete missing app fields.
- Do not require phone number in this phase.

### 6. Deferred wallet creation

- Do not auto-create the embedded wallet immediately after auth.
- Use Openfort’s deferred/manual wallet-creation path supported by the installed SDK version.
- Current SDK examples for the React stack show manual handling through wallet config with `connectOnLogin: false`; confirm the exact option against the repo’s pinned Openfort version during implementation.
- Only create/connect the embedded wallet after the user is qualified and profile verification is complete.

## Backend Plan

### 1. Existing-user branching support

- Return an explicit `is_new_user` flag from the Openfort exchange flow, or add a dedicated authenticated lookup path that the frontend can use immediately after Openfort auth.
- Apply questionnaire-derived `role` and `type` only for new-user provisioning.

### 2. Profile update endpoint

- Add a lean authenticated profile update route such as `PATCH /v1/me`.
- Allow profile verification/completion without coupling it to wallet creation.

### 3. Validation hardening

- Validate questionnaire-derived enum values explicitly instead of silently defaulting.
- Keep exchange request body fields optional at the transport layer so existing users can still exchange with token-only requests.

## Implementation Order

1. Update provider config to support deferred wallet creation.
2. Make `/` public and `/login` redirect to `/`.
3. Update auth-session orchestration to branch existing users vs new users after Openfort auth.
4. Build the qualification flow for new users only.
5. Reuse the existing waitlist endpoint for unqualified users.
6. Add backend profile update support.
7. Build the profile verification/completion page.
8. Trigger wallet creation only after qualification and profile completion.
9. Remove stale Particle deployment/env references.
10. Run validators and manual QA.
