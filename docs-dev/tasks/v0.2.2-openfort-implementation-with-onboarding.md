# v0.2.2 Openfort Implementation With Onboarding

**Date:** 2026-04-12
**Status:** Approved plan (revised)
**Supersedes:** `docs-dev/tasks/v0.2.1-openfort-implementation-part-2.md`

## Goal

Finish the Openfort rollout with a lean onboarding flow that:

1. keeps Openfort as the single auth entry point (no separate login/register buttons)
2. uses `connectOnLogin: false` so Openfort authenticates without creating a wallet
3. checks the backend to determine whether the Openfort user already exists
4. sends only new users through the qualification questionnaire
5. defers wallet creation until after qualification
6. routes disqualified users to a non-resident/waitlist contact form

## Product Direction

- `/` becomes the public landing page with a single Openfort button.
- `/login` redirects to `/`.
- Existing users go straight from Openfort auth into the app (no onboarding).
- New users are qualified before the backend provisions them and a wallet is created.
- Disqualified users submit a non-resident contact form and stop there.
- No phone number, no personal-details form, no profile-verification page in this phase.
- If Openfort doesn't collect enough user data during auth (e.g. name via Email OTP), that gap will be addressed in a follow-up phase after manual QA, not preemptively.

## Design Decision: Auth Before Qualification

The old flow (landing-pro) showed the questionnaire first, then redirected to a separate dashboard app for Particle registration via a cookie handoff. With Openfort, we use a single app and a single button:

1. User clicks the Openfort button → authenticates (Google, Email OTP, etc.).
2. No wallet is created (`connectOnLogin: false`, `embeddedState` stays at `EMBEDDED_SIGNER_NOT_CONFIGURED`).
3. Frontend calls the backend with the Openfort access token to check if the user already exists.
4. **Existing user** → backend session exchange → enter the app.
5. **New user** → qualification questionnaire → if qualified, exchange with role/type → create wallet → enter the app.

This eliminates the two-app architecture, the cookie handoff, and the need for separate login/register buttons. Openfort handles both login and signup as one flow — the backend lookup determines which path the user takes.

## Clean / Lean / Defaults-First Principles

- Keep Openfort stock UI and modal behavior wherever possible.
- Do not restore the old Particle cookie handoff or popup chain.
- Keep frontend state local (`sessionStorage` for short-lived onboarding intent only).
- Keep backend responsibility limited to app identity, session, profile, and authorization.
- Do not couple onboarding to custom wallet UI.
- Do not add a profile-verification page preemptively. Start lean, add later if needed.

## Backend Role

The backend is not the wallet creator. Its job is to:

1. verify the Openfort session/token
2. find the InfraFund user by `openfort_user_id`
3. create or refresh the InfraFund app session
4. expose app-level identity/status/profile endpoints
5. store app-specific profile data such as role, type, and completion fields

Openfort remains responsible for authentication, embedded wallet lifecycle, and recovery.

## Qualification Questionnaire Specification

Ported from `landing-pro/src/component/SurveyOnlyForm.tsx`. The original had 6 steps; we keep steps 1–3 and the non-resident form (step 4). Steps 5–6 (personal details + email/ToS) are dropped because Openfort already collected email/name during auth.

### Step 1 — "What brings you to InfraFund?" (role selection)

| Option | Role value | Description |
|---|---|---|
| Raise Funds (Project Developer) | `client` | Project owner/developer seeking capital |
| Invest in Assets (Investor) | `investor` | Wants to fund green projects |
| Manage Construction (Contractor) | `contractor` | EPC/General Contractor |
| Join the DAO (Governance Member) | `governance` | Protocol governance participant |

Note: The landing-pro code uses `dao` as the role value for governance; the backend uses `governance`. Map `dao` → `governance` at the point of exchange.

### Step 2 — "Are you an Individual or Organization?" (type selection)

Two cards: **Individual** or **Organization**. Maps to `type: "individual" | "organization"`.

### Step 3 — "First, please confirm the following." (qualification checkboxes)

**Individual (3 checkboxes, all start checked):**

| Checkbox | Key | Disqualification message |
|---|---|---|
| I am currently a UK resident | `ukResident` | We are currently only accepting investments from UK residents. |
| I have a valid UK national insurance number | `niNumber` | A valid UK national insurance number is required. |
| I am at least 18 years old | `over18` | We do not provide services to individuals under 18 years old. |

- If `ukResident` or `niNumber` is unchecked → disqualified → show non-resident contact form.
- If `over18` is unchecked → blocked (cannot continue), but not sent to contact form.

**Organization (3 checkboxes, all start checked):**

| Checkbox | Key | Disqualification message |
|---|---|---|
| Our company is based in UK | `ukBased` | We are currently only accepting investments from UK-based companies. |
| We have a valid UK Companies House number | `companyHouse` | A valid UK Companies House number is required. |
| Our company is currently active | `active` | We only accept applications from currently active companies. |

- If any checkbox is unchecked → disqualified → show non-resident contact form.

### Non-resident contact form (disqualified users)

Shows a disclaimer: "Unfortunately, at this point in time, we cannot accept investments from [people who are not UK residents / organizations who are not in the UK]."

Fields:
- First Name / Last Name (individual) or Contact Full Name / Company Name (organization)
- Country (dropdown from backend `/locations` endpoint)
- Email

Submits to the backend non-resident endpoint (`/non-resident/individual` or `/non-resident/company`) with captcha. On success, close the modal.

## Frontend Plan

### 1. Deferred wallet creation config

Set `connectOnLogin: false` in the `walletConfig` passed to `OpenfortProvider` in `src/lib/openfort-config.tsx`.

```tsx
walletConfig={{
  shieldPublishableKey: process.env.NEXT_PUBLIC_SHIELD_API_KEY,
  ethereum: { chainId: targetChainId },
  connectOnLogin: false,  // Auth without wallet creation
  createEncryptedSessionEndpoint: "/api/auth/encryption-session",
}}
```

After qualification, create the wallet via:
```tsx
const { create } = useEthereumEmbeddedWallet();
await create({ recoveryMethod: RecoveryMethod.AUTOMATIC });
```

### 2. Public/auth routing cleanup

- Make `/` public — render the landing page with the Openfort button.
- Redirect `/login` to `/`.
- Replace the current implicit "everything except /login is private" rule in `main-layout.tsx` with an explicit private-route list.

### 3. Existing-user detection after Openfort auth

- After Openfort auth succeeds, call a backend endpoint to check whether the user exists by `openfort_user_id`.
- If the user exists → complete backend session exchange → enter the app.
- If the user is new → hold the Openfort session client-side → show qualification questionnaire.
- This requires either:
  - (a) The existing exchange endpoint to return an `is_new_user` flag, or
  - (b) A new lightweight lookup endpoint (e.g. `GET /v1/auth/openfort/check`) that returns `{ exists: boolean }` without creating a user.

Option (b) is leaner — it avoids creating a user record before qualification.

### 4. Qualification questionnaire (new component)

- Build as a modal with steps 1–3 from the spec above.
- Port the UI patterns from `landing-pro/src/component/SurveyOnlyForm.tsx` but adapted to the front-pro design system (existing `Modal`, `FormInput`, `CustomButton`, `CustomCheckbox` components in `src/components/ui/`).
- Store qualification result in `sessionStorage` (`role`, `type`) until exchange completes.
- On qualification success → call backend exchange with `role` and `type` in request body → create wallet → redirect to `/home`.
- On disqualification → show the non-resident contact form.

### 5. Non-resident contact form (disqualified users)

- Reuse the backend's existing non-resident endpoints.
- Show the country dropdown (fetch from backend `/locations` endpoint).
- Submit with captcha protection.
- On success → show confirmation → close modal.

### 6. Wallet creation after qualification

- Only after the backend exchange succeeds and the user is provisioned.
- Use `useEthereumEmbeddedWallet().create({ recoveryMethod: RecoveryMethod.AUTOMATIC })`.
- Show a brief loading state during wallet creation ("Setting up your wallet...").
- Once `embeddedState` reaches `READY` (state 4) → redirect to `/home`.

### Required backend changes

1. **New-user detection** — Add one of:
   - (preferred) `GET /v1/auth/openfort/check` — authenticated endpoint that returns `{ exists: boolean }` without creating a user.
   - (alternative) Add `is_new_user: boolean` field to the exchange response DTO.

2. **Non-resident endpoints** — Verify that `POST /v1/non-resident/individual` and `POST /v1/non-resident/company` (or equivalent waitlist endpoints) exist in backpro. If they only exist in landing-pro's backend proxy, they need to be added or confirmed as reachable from front-pro.

3. **Profile update (deferred)** — Not needed in this phase. If Openfort doesn't provide sufficient user data (name via Email OTP), add `PATCH /v1/me` in a follow-up.

## Resolved Questions

1. **Captcha for non-resident form** — Reuse the existing reCAPTCHA site key from landing-pro. Add `NEXT_PUBLIC_RECAPTCHA_SITE_KEY` to front-pro's env config. The reCAPTCHA v3 script is loaded via `next/script` and tokens are generated client-side with `grecaptcha.execute()`. Port the small `getRecaptchaToken()` utility from `landing-pro/src/utils/recaptcha.ts`.

2. **Non-resident endpoints** — They exist **directly in backpro**, not just as landing-pro proxies. Landing-pro's `/api/non-resident/*` routes were just Next.js proxies to backpro. Front-pro can call backpro directly:
   - `POST /v1/non-resident-waitlist/individual` (first_name, last_name, email, country_id + `X-Captcha-Token` header)
   - `POST /v1/non-resident-waitlist/company` (+ company_name)
   - `GET /v1/locations/countries` (for country dropdown, no captcha)

3. **Name collection** — Defer to a later phase. Google auth provides name + email; Email OTP provides email only. If name is missing, show it on the user's account/profile page after they enter the app and let them fill in the blanks. Do not add a pre-entry name collection step in this phase. Email/account changes should go through Openfort's own account management flow.
